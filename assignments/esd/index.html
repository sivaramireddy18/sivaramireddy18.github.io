1. Problem & engineering objective

Modern embedded workloads need deterministic control as well as computationally intensive signal or sensor processing. The proposed system separates those responsibilities between a Cortex-M33 control domain and a Cortex-M55 compute domain.

Problem

A single execution domain may have to perform acquisition, control, communication and heavier processing at the same time, creating timing and power trade-offs.

Objective

Design a heterogeneous embedded architecture and validate its functional behavior, inter-core communication and end-to-end timing.

Inputs

ADC/I²C/SPI sensor samples, timer events and configuration commands.

Outputs

Processed results, UART diagnostics and optional GPIO/actuator indication.

Firmware flow

BOOT ↓ CM33 initialization → UART + timer + sensor interface ↓ Acquire sample → buffer → packetize ↓ Signal CM55 through IPC ↓ CM55 validates packet → processes block → timestamps execution ↓ Return result/status through IPC ↓ CM33 validates result → UART/GPIO response ↓ Repeat / handle error

5. Firmware design

CM33 responsibilities

  1. Initialize platform and observability.
  2. Configure periodic acquisition.
  3. Capture samples into a bounded buffer.
  4. Generate IPC request.
  5. Handle completion/error events.
  6. Publish timing and validation logs.

CM55 responsibilities

  1. Wait for a valid work packet.
  2. Check sequence/count/status.
  3. Run the processing kernel.
  4. Measure processing duration.
  5. Generate result/status.
  6. Return ownership to CM33.

Illustrative Embedded C structure

typedef struct { uint32_t sequence; uint32_t timestamp; uint16_t sample_count; uint16_t samples[16]; uint32_t status; } sensor_packet_t; /* CM33 */ acquire_samples(&packet); ipc_send_sensor_packet(&packet); /* CM55 */ if (validate_packet(&packet)) { result = process_sensor_block(packet.samples, packet.sample_count); ipc_send_result(&result); }

The code is intentionally hardware-agnostic. Vendor-specific startup, register definitions, linker configuration and IPC primitives must be mapped only when the actual target environment is available.

12. Implementation roadmap

  1. CM33 boot and UART observability.
  2. CM55 startup and basic heartbeat.
  3. Deterministic IPC handshake.
  4. Sensor packet transfer with bounded buffer.
  5. ADC/sensor integration.
  6. Timer/SysTick and NVIC configuration.
  7. CM55 processing kernel and result return.
  8. Timestamp instrumentation.
  9. Functional, negative and stress validation.
  10. Capture evidence and compare measured performance.

13. Engineering trade-offs

DecisionBenefitTrade-off
Separate control and compute domainsClear responsibility and potential concurrencyIPC and synchronization overhead
Shared-memory packetsEfficient bulk data exchangeOwnership/cache/memory-ordering concerns
Interrupt-driven eventsResponsive system behaviorPriority design and debugging complexity
UART diagnosticsSimple observabilityBandwidth and instrumentation overhead

14. Lessons & next improvements

  • Validate the communication mechanism before optimizing the processing kernel.
  • Measure end-to-end behavior; core execution time alone is insufficient.
  • Keep shared-buffer ownership and synchronization explicit.
  • Separate analytical models from experimental measurements.
  • Next: add real traces, hardware measurements, a reproducible benchmark and a final results dashboard.
